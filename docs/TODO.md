# Umbra Task and TODO List

This list contains the technical tasks planned for the step-by-step implementation of the project.

> **Scope Note (ADR-027):** Tasks are divided into two sections by delivery priority.
> - **Section A — MVP (v1.0):** Core cryptography, the Arti P2P network, protocol masking, the Linux TUI, and basic security/test infrastructure. v1.0 is released with exactly this scope.
> - **Section B — v2 and Later:** Android client, GTK4 GUI, mesh/mixnet, PQ-MLS, active deception, and hardware side-channel defenses. These items are not cancelled; they are planned for after v1.0.

## B.2 Asynchronous Group Encryption (`umbra-group`)

- [x] PQ-MLS TreeKEM asynchronous group encryption engine — single-cell increment LANDED (ADR-033) as `crates/umbra-group`, built on OpenMLS 0.9.0 with the `libcrux-provider` (pure Rust, ADR-033) rather than a from-scratch TreeKEM reimplementation. `umbra group create` / `export-keypackage` / `add` / `send` cover the create-a-cell, publish-a-`KeyPackage`, add-a-member (Commit+Welcome fan-out), and send-an-application-message flows; inbound processing (`umbra_group::inbound::process_inbound_group_frame`) is wired into `umbra serve`'s real Tor inbound loop and decodes Welcome/Commit/application-message frames, persisting the updated group state after every processed message (not just Commits — the secret tree advances on every decrypt). Group state is persisted as one whole-`MlsGroup`-blob AEAD-encrypted file per group (`<keystore_dir>/groups/<name>.enc`), not a hand-implemented `StorageProvider` (ADR-033). Wire-level: a new leading connection-type marker byte (`CONNECTION_TYPE_PQXDH`/`CONNECTION_TYPE_GROUP`, `umbra_net::messenger::peek_connection_type`) lets a receiver distinguish a two-party PQXDH handshake from a group frame on the same raw stream — the first change to that wire format since its original design, deliberately minimal and covered by both the existing PQXDH regression suite and new marker-specific tests (ADR-033). Hermetically unit- and integration-tested, including a full 3-party create→add→send→receive end-to-end test (`crates/umbra-group/tests/hermetic_multi_party.rs`); lints clean.
  - **Ciphersuite caveat (honest, not hidden):** `MLS_256_XWING_CHACHA20POLY1305_SHA256_Ed25519` — X-Wing hybrid KEM (X25519 + ML-KEM-768) for TreeKEM, but classical Ed25519 (not a PQ signature scheme) for leaf-node/message signing, because `draft-ietf-mls-pq-ciphersuites` does not yet define a full post-quantum MLS ciphersuite (KEM + signature) in OpenMLS 0.9.0. Group content stays hybrid-KEM-protected against harvest-now/decrypt-later, but a future large-quantum-computer break of classical ECDLP could retroactively forge handshake authentication. Migration is planned once OpenMLS ships a full PQ ciphersuite (ADR-033).
  - **OUT OF SCOPE for this increment (explicit, tracked residuals — not silently dropped; each residual has a numbered follow-up task below with its ruled resolution approach, decided 2026-09-10):**
    - **Member removal** — no `remove_members`/Remove-Commit path exists; a cell can only grow, never shrink. → follow-up task B.2.2.
    - **Key rotation** — no periodic/on-demand `update`/re-key operation; TreeKEM's own forward secrecy on add/remove is exercised, but there is no standalone rotation trigger. → follow-up task B.2.3.
    - **Sub-groups** — no nested/branched group support; one flat member list per cell. DELIBERATELY out of scope with NO follow-up task: MLS has no group-hierarchy concept, a real solution is new protocol research, and the operational need is served by running multiple flat cells (e.g. a "core" cell plus a "wide" cell).
    - **Large-group scalability** — validated only at small (3-party) scale; no testing or optimization for OpenMLS's tree-based scaling at higher member counts. → follow-up task B.2.5.
    - **Full ML-DSA (or other PQ) signature ciphersuite** — see the ciphersuite caveat above; blocked on upstream OpenMLS support. → follow-up task B.2.7 (monitor-only, no code).
    - **Mesh/Nym transport group-inbound support** — group frames are Tor-only. `mesh_serve.rs` has its own separate inbound path that explicitly rejects an incoming `CONNECTION_TYPE_GROUP` marker ("mesh transport: group frames are not yet handled"); `umbra-nym-cli` has no group-inbound handling at all. Both transports can carry a two-party PQXDH session today but not a group cell. → follow-up task B.2.4.
    - **Roster-bootstrapping for a newly joined member (real functional gap).** `GroupRoster` — Umbra's own peer-name-to-leaf-index bookkeeping, never carried by MLS itself — is populated only by `create_group`'s and `add_member`'s own local view (the member performing the add already knows the new peer's name). The inbound `Welcome`-processing path (`process_welcome`) has no such mapping to draw from and persists an **empty** roster for the newly joined member, by ruling (see `crates/umbra-group/src/inbound.rs`'s module docs). Since `send_group_message`/fan-out delivery resolve peers to contact via the roster, a member who joins via Welcome will successfully receive and decrypt group traffic, but their own `umbra group send` fans out to **zero** recipients until some future mechanism bootstraps their view of the other members' peer-name mappings (e.g. a protocol extension, or an out-of-band exchange). This gap is real today and is exercised only via the hermetic end-to-end test's own direct, test-only roster patching (a legitimate simulation of what the B.2.1 mechanism will produce, not production code). → follow-up task B.2.1.

- [ ] **B.2.1 Roster-bootstrapping via an application-level `RosterSync` message (the most load-bearing residual; do FIRST).** Close the empty-roster gap without touching MLS itself: the member performing `add_member` sends a full roster snapshot (peer-name ↔ leaf-index) as a new typed, application-level group-frame variant immediately after the Welcome, and again to ALL members after every subsequent add (Commits carry no Umbra peer names, so every member's roster needs the refresh). `process_inbound_group_frame` gains a `RosterSync` variant that populates the receiver's `GroupRoster`. Security reasoning: the message rides the group's own AEAD channel and the adder's already-authenticated pairwise delivery, and the adder already controls membership — the trust model is unchanged. A full snapshot per add is trivially cheap at current cell sizes. Rejected alternative: embedding peer names in MLS leaf-credential extensions would mean modifying OpenMLS's internals — disproportionate risk for zero gain. Acceptance: the hermetic end-to-end test's current test-only direct roster patching is replaced by the real mechanism (alice adds bob and carol, and both can send without any test-side patching).
- [ ] **B.2.2 Member removal via OpenMLS's existing `remove_members` path (highest security value: revocation).** `umbra group remove <cell> <peer>`: look the peer's leaf index up in the `GroupRoster`, build a Remove proposal + Commit with OpenMLS 0.9.0's stock API, fan the Commit out to the REMAINING members over the same delivery infrastructure `add_member` already uses, and delete the peer from the roster. The removed member receives nothing; TreeKEM path advancement leaves it able to decrypt past traffic but nothing new (the protocol's native property, no extra code). Acceptance: extend `crates/umbra-group/tests/hermetic_multi_party.rs` — after carol is removed she can no longer decrypt alice's new message while bob still can.
- [ ] **B.2.3 On-demand key rotation via `self_update` (`umbra group rotate`).** OpenMLS 0.9.0 already ships `self_update`; the command produces a single Update Commit and pushes it through the same fan-out as B.2.2 — no roster change at all. Deliberately manual-only: no automatic/periodic rotation policy in this task (a scheduler, if ever wanted, is a separate UX decision). B.2.1–B.2.3 share one fan-out infrastructure and one hermetic test file, and are intended to land as ONE increment.
- [ ] **B.2.4 Mesh/Nym transport group-inbound wiring.** `process_inbound_group_frame` is already transport-agnostic (it consumes a byte slice); `mesh_serve.rs` routes an inbound `CONNECTION_TYPE_GROUP` marker to it instead of rejecting, and `umbra-nym-cli`'s receive path does the same over its duplex bridge. Pure wiring plus one hermetic test per transport — no protocol work.
- [ ] **B.2.5 Large-group scalability — benchmark FIRST, optimize only on measurement.** This is an information gap, not a code gap: add a hermetic benchmark test at N=10/50 members measuring wall-time and peak memory for create/add/send. TreeKEM is O(log N) by construction; the expected bottleneck is Umbra's per-member pairwise PQXDH fan-out over Tor, not OpenMLS. If (and only if) measurements show a real problem, the first remedies are engineering — session reuse, parallel fan-out — never protocol changes. No optimization without numbers.
- [ ] **B.2.6 Persistence-envelope versioning (harden, don't rewrite).** Add a version tag to the `PersistedState` AEAD wrapper and to the key-package store files, and keep `openmls` version-pinned. Whole-blob persistence's dependence on `MemoryStorage`'s public map layout is already fail-closed — an upstream layout change is a COMPILE error, never silent data corruption — so a hand-implemented 80-plus-method `StorageProvider` remains disproportionate and the sqlite-provider remains ruled out (the ADR-032/ADR-033 `links = "sqlite3"` conflict stands). Small chore.
- [ ] **B.2.7 Full post-quantum signature ciphersuite — BLOCKED UPSTREAM, monitor-only (no code).** No standardized PQ signature ciphersuite for MLS exists (`draft-ietf-mls-pq-ciphersuites` defines hybrid KEMs only), and layering Umbra's own ML-DSA underneath MLS framing stays rejected — it would fork the protocol's authentication properties (ADR-033). Action: track the draft and OpenMLS releases, and migrate `umbra-group`'s ciphersuite when a full-PQ (KEM + signature) suite ships. Mitigating fact documented in THREAT_MODEL.md: Welcome/Commit fan-out already rides per-member authenticated PQXDH channels, which narrows the practical forgery surface below what the ciphersuite caveat alone implies.
